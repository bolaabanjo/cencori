Basecode supports [Model Context Protocol](/docs/mcp) servers, so you can give it tools it does not ship with — an internal API, a database, an issue tracker, or anything else with an MCP server.

## Add a server

Basecode generates its runtime configuration on every launch, so that file is not the one to edit. Put your own configuration in `basecode.user.toml` inside the Basecode agent home directory, and Basecode merges it in after its own settings.

On macOS:

```
~/Library/Application Support/Basecode/agent-home/basecode.user.toml
```

Add a server as a `mcp_servers` table:

```toml
[mcp_servers.my_tools]
command = "npx"
args = ["-y", "@example/my-mcp-server"]
startup_timeout_sec = 20

[mcp_servers.my_tools.env]
MY_TOOL_TOKEN = "..."
```

Restart Basecode to pick up the change.

## Useful options

- `enabled_tools` — an allow-list. When set, only the tools you name are registered, which keeps a large server from crowding the agent's tool list.
- `disabled_tools` — a deny-list applied after `enabled_tools`.
- `startup_timeout_sec` — how long to wait for the server to start and list its tools.
- `enabled = false` — keep a server configured but switched off.

## The Cencori server

Basecode already runs Cencori's own MCP server for documentation lookup, limited to its keyless read-only tools, so the agent can answer questions about Cencori from current documentation rather than from memory. You do not need to configure it.

If you want the rest of what `@cencori/mcp` offers — gateway reads, memory, sessions, governance — add it yourself under a different name with your own API key. See the [MCP server documentation](/docs/mcp) for the tool tiers and the environment variables that enable them.

## Secrets

`basecode.user.toml` is a plain file on your machine. Prefer referencing an environment variable your shell already provides over writing a long-lived token into it, and treat it like any other local credential file.
